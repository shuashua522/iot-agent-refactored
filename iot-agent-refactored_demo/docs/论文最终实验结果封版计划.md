# 论文最终实验结果封版计划

> 计划版本：v1.0
>
> 建立日期：2026-07-25
>
> 目的：把当前“可运行的实验原型 / 开发态结果”推进到可以支撑论文最终实验章节的、可复现、可审计、可解释的正式结果。
>
> 本文档是执行计划，不是实验方案本身。后续如果代码、场景、指标或环境发生变化，应递增计划版本，在文末记录变更原因；不得静默修改封版口径。

## 一、封版目标

最终封版至少需要同时满足以下条件：

1. 36 个场景的脚本、ground truth、指标映射和 RQ 标签完全同步，且每个场景都能在正式 runner 中被执行和判定。
2. Ours、B0-B5、全部预注册 ablation 使用相同的 world、场景、seed 规则和评测口径；Oracle 与 Agent 的适用范围明确，不混淆汇报。
3. 每个正式配置完成预注册数量的独立 seed 运行：Oracle 主结果使用 `N=30`，Agent / 次要结果使用 `N=20`；如实际无法达到，必须在论文中明确降级为开发态或补充实验。
4. 任务成功判定同时检查动作语义、澄清行为、记忆状态断言和最终设备状态，不能出现“trace 失败但 TSR=1”的矛盾。
5. 主要指标、次要指标、统计检验、置信区间和成本口径固定，并由脚本自动生成，禁止手工挑选结果。
6. 所有正式结果均能追溯到：代码提交、配置、world 版本、scenario 版本、system policy、seed、原始 trace 和生成脚本。
7. 只有通过全部封版门槛的结果才能进入论文主表；未通过的结果只能放在开发记录、消融探索或局限性部分。

## 二、当前基线与硬问题

当前仓库已经有记忆服务、冻结 world、36 个场景、baseline / ablation、trace、报告和 `46/46` smoke tests，但还不是最终实验结果。当前必须优先处理的事实如下：

- 已落盘的 configured 结果实际只有 `seed=1001`，统计文件中的 `count=1`、`paired_count=1` 不能支撑显著性检验。
- 36 个场景中目前是 31 个 Oracle 场景和 5 个 Agent 场景；这两个集合不能在同一张“统一任务成功率”主表中直接混合。
- Ours 的 Oracle 开发态结果存在 `TSR=1.0` 但 manifest 有 15 个失败任务的矛盾，说明当前成功判定和 TSR 指标不一致。
- Agent planner 仍包含启发式 fallback，尚未形成可作为论文主结论依据的真实端到端 Agent 实验路径。
- 部分场景仍接近“可加载骨架”，部分 ablation 在当前场景集合上没有产生可观测差异。
- 当前报告和统计链已经能生成产物，但“能生成”不等于“统计口径正确”。

上述问题没有解决前，不得把当前结果称为论文最终结果。

## 三、执行总顺序

必须按以下依赖顺序推进。后一个阶段不得绕过前一个阶段的失败门槛：

`P0 口径冻结` → `P1 判定与指标修正` → `P2 场景与覆盖封闭` → `P3 系统与对照有效性` → `P4 正式多 seed 运行` → `P5 统计与结果审计` → `P6 可复现封版` → `P7 论文写入`

## 四、阶段计划与验收门槛

### P0：冻结实验口径

目标：先把“什么算成功、每个指标怎么算、哪些结果可进论文”写死。

任务：

- 对照《实验方案-v3(1)-中文翻译.md》，建立 36 场景的 `scenario_id → category → RQ → primary/secondary metric` 矩阵。
- 明确 Oracle 和 Agent 的实验角色：Oracle 用于机制与记忆闭环控制实验，Agent 用于端到端可行性与安全路径；不能把两者无说明地合并。
- 明确主指标、次指标、成本指标和统计单位。建议主指标至少包括 TSR、WDR、CB、PM、SRR / 相关 RQ 指标；其余作为次指标。
- 明确重复单位是 seed、scenario 还是 task instance，明确跨 seed 和跨场景的聚合方式。
- 把所有“开发态”“探索性”“正式结果”的目录和命名规则写入配置与文档。

验收证据：

- 一份可审计的覆盖矩阵。
- 一份固定的指标定义与公式文档或代码注释。
- 代码配置中没有隐式改变正式实验口径的默认值。

封版门槛：没有口径冻结，不进入代码大改和正式运行。

### P1：修正任务成功判定与指标一致性

目标：消除“动作失败但 TSR 成功”的核心错误。

任务：

- 将动作执行结果分为至少：`action_success`、`clarification_success`、`memory_assertion_success`、`final_state_success`、`task_success`。
- `planner.select` 不能被当作真实 Home Assistant service；如果场景要求 `light.turn_on`，必须检查最终执行的 service、entity 和 args。
- 对复合任务逐步检查动作序列、前置条件、后置状态和最终状态。
- 对 `expect_action`、`expect_no_action`、`expect_memory`、`expect_final_state` 的失败统一写入结构化 assertion result，不只写字符串。
- 重新定义 TSR：只在任务要求的动作 / 澄清 / 记忆状态 / 最终状态全部满足时计为成功；不能仅比较两个可能为空或被错误覆盖的状态字典。
- 增加失败分类：错误设备、错误 service、未澄清、错误记忆生命周期、world 执行失败、断言失败、Agent 输出不可解析。

验收证据：

- 原先失败的 A1 等场景在 trace 中能清楚显示失败原因；修正后成功任务的 `outcome`、`TSR` 和 manifest `failed_task_ids` 一致。
- 构造至少 5 个反例测试：最终状态相同但 service 错误、动作正确但状态错误、应澄清却直接执行、应静默却产生动作、记忆断言失败。
- `failed_task_ids` 数量与任务成功率逐项可复算。

封版门槛：任何正式 run 出现 `outcome=failure` 但 TSR 仍计为成功的情况，都必须阻止封版。

### P2：补齐 36 场景和 ground truth

目标：让测试集从“有 36 个文件”变成“36 个完全指定、可解释、可复现的正式任务”。

任务：

- 逐场景核对时间、初始 world、初始 memory、用户话语、memory ops、预期检索、预期澄清、动作、最终状态和失败注入。
- 给每个场景补齐唯一且非空的 ground truth，避免通过空字典或默认状态获得虚假的成功。
- 确认 A-H 类场景分别覆盖 RQ1-RQ5，且同一 RQ 至少有正向和负向路径。
- 确认 F7 delete / privacy、F6 成功 merge、G5 瞬时状态不持久化、H1/H2 查询阈值等新增主张都有可执行断言。
- 确认双标注文件不是空占位；如果采用专家标注，记录标注规则和一致性计算；如果全部是确定性脚本，明确说明不把占位标注冒充人工标注。
- 为每个场景增加 `expected_outcome_class` 和覆盖说明，方便报告按场景审计。

验收证据：

- 36 个场景全部通过 schema 校验。
- 36 个场景全部能运行，不允许因缺少 fixture、不可执行 action 或空 ground truth 被跳过。
- 场景覆盖矩阵显示每个主要 RQ、主要指标和关键设计主张至少被一个正式场景覆盖。
- 每个场景至少有一条正向或负向可验证断言，不接受只有 `say` 没有可验证结果的场景。

封版门槛：如果某场景只能依赖 runner 特判或人工解释才能判定，不进入论文主实验。

### P3：确认 Ours、baseline、ablation 真正有效

目标：确保比较的是不同机制，而不是同一套启发式代码改了几个配置名。

任务：

- 审计 `SystemConfig` 每个开关是否真实改变执行语义，并为每个开关指定至少一个敏感场景。
- 确认 B0-B5 的行为边界与方案一致，尤其是 B4 大上下文和 B5 Generative Agents 类比基线。
- 对每个 ablation 建立机制→场景→预期变化→指标的映射，不能接受所有结果完全相同而没有解释。
- Agent 路径必须记录原始模型输出、解析结果、工具调用、world 反馈和失败原因；启发式 fallback 只能作为单独的 fallback 实验，不能伪装成正式 Agent 结果。
- 如果本阶段仍以 Oracle 为主，论文中必须明确 Oracle 是受控 planner，不将其描述为完整真实 Agent。

验收证据：

- 每个 baseline / ablation 至少有一个回归测试证明其开关被触发。
- 每个预注册机制至少有一个场景能观察到预期方向的行为差异，或者有正式的“该机制在此测试集上不敏感”解释。
- Agent 正式路径不依赖未记录的 fallback。

封版门槛：无法区分的 baseline / ablation 不进入最终比较表，只能保留在开发记录。

### P4：执行正式多 seed 实验

目标：按预注册协议获得真正的重复实验数据。

任务：

- 在确认环境、依赖、模型、温度、embedding、world 和代码提交后，执行 Oracle `N=30` primary seeds。
- 执行 Agent / secondary 结果 `N=20`，并明确它是次要实验还是独立主实验。
- 每个 system、planner mode、scenario、seed 都写入独立 trace；不得因重复运行覆盖 trace。
- 固定随机种子来源、模型版本、采样温度、重试策略和失败处理策略。
- 运行前清理或隔离旧开发态结果，正式结果使用新 run id，不把旧文件混入聚合目录。
- 正式运行过程中不根据中间结果修改场景、指标或系统配置；如必须修改，递增实验版本并重新开始正式运行。

验收证据：

- 每个正式 run 的 manifest 显示正确 seed 数、scenario 数和系统配置。
- 每个正式配置的 `metrics.by_seed.json` 数量符合协议：Oracle 30，Agent 20。
- 所有 seed 都有 trace，失败任务也必须有完整 trace，不能静默丢弃。
- 运行结果绑定 git revision、配置快照、world version、scenario version 和 system policy version。

封版门槛：任一主要配置仍是 `count=1` 或缺 seed，不能进入论文主表。

### P5：统计与结果审计

目标：让结果能够被复算、解释和诚实地汇报。

任务：

- 优先按预注册单位做 paired comparison；确认配对的是同一 seed、同一 scenario、不同 system。
- 选择适合指标分布的统计检验，不把 `paired_count=1` 的结果当作显著性证据。
- 输出均值、标准差 / 标准误、95% CI、效应量、校正后的 p 值，并记录检验方法和多重比较校正方法。
- 对二元指标和比例指标检查是否需要 bootstrap、置换检验或分层聚合，避免直接套用不适合的 Cohen's d。
- 报告 overall、按 category、按 RQ、按 scenario 的结果，避免少数容易场景掩盖失败场景。
- 审计主要异常：TSR 与 outcome 不一致、空 ground truth、零分母、指标全为 0、某配置完全相同、失败任务缺 trace。
- 重新生成表格、图、Markdown 报告和 significance summary；报告中明确开发态结果与正式结果的边界。

验收证据：

- 任意论文表格中的数字都能从原始 trace 重新生成。
- 统计报告列出样本量和有效样本量，不隐藏失败或缺失任务。
- 主要结论在不同聚合方式下不会因一个场景或一个 seed 而完全反转；若会，必须作为限制报告。

封版门槛：统计脚本无法从干净结果目录重建论文表格时，不封版。

### P6：可复现性与最终封版

目标：冻结一份第三方可以检查的最终实验工件。

任务：

- 新建正式结果 run id，隔离所有 `dev`、`check`、`test` 结果。
- 保存最终配置、依赖版本、Python 版本、模型 / embedding 信息、git commit、运行命令和开始结束时间。
- 从干净结果目录重新执行报告生成链，验证不会依赖旧的聚合文件或本地缓存。
- 运行完整 smoke、场景 schema 校验、trace schema 校验、结果一致性审计和统计重建。
- 检查工作区状态；代码、场景、指标、文档和生成脚本在同一组提交中提交。
- 在 `docs/实验结果摘要.md` 标注正式 run id、样本量、最终指标和限制；在 `docs/实验实现进展.md` 标记完成度，但不能夸大结论。

最终封版证据包至少包括：

- 正式配置文件和版本快照。
- 36 场景及 ground truth / 标注资产。
- 每个正式配置的 manifest。
- 原始 trace 和 maintenance trace。
- 聚合指标、per-scenario 指标、seed 级指标。
- 论文表格、图、统计检验摘要。
- 运行日志、依赖信息和 git revision。
- 最终限制说明和失败样本审计表。

封版门槛：任何结果如果无法从 trace 和配置逐项追溯，就不能作为最终结果提交论文。

### P7：写入论文

只有 P0-P6 全部通过后，才进入论文实验章节。建议写作顺序：

1. 实验设置：world、场景、RQ、baseline、ablation、seed 和指标。
2. 实现细节：memory schema、生命周期、置信度、检索门控、反馈和治理。
3. 主结果：按预注册主要指标展示 Ours 与基线，并报告样本量和不确定性。
4. 消融结果：只解释已通过机制敏感性审计的 ablation。
5. 分析结果：按 RQ、category、场景类型和失败类别分析。
6. 成本与安全：上下文成本、澄清负担、安全门控和失败规避。
7. 限制：仿真 world、Oracle / Agent 差异、样本来源、外部依赖和未覆盖能力。

论文中必须明确区分：

- 正式结果：满足 P0-P6 的 run。
- 开发态结果：用于调试和回归，不参与主结论。
- 探索性结果：未预注册或样本量不足，只用于提出后续假设。

## 五、建议的 Goal 模式拆分

后续每次 Goal 不要同时承担所有阶段，建议按以下目标逐个完成：

### Goal 1：修复成功判定与指标一致性

完成 P1；优先修正 action 语义、assertion 结果、TSR 和失败分类；通过反例测试后再继续。

### Goal 2：完成 36 场景与覆盖矩阵审计

完成 P0 和 P2；输出场景审计清单，补齐空 ground truth、缺失断言和 RQ 映射。

### Goal 3：完成 baseline / ablation / Agent 路径审计

完成 P3；确认每个系统配置真的改变行为，并明确 Oracle、Agent 和 fallback 的论文身份。

### Goal 4：重建正式运行入口和结果隔离

完成 P4 的运行准备，不急于长时间运行；先验证 seed 数、目录隔离、manifest 和断点失败行为。

### Goal 5：执行正式多 seed 运行

完成 P4；只使用已经冻结的代码、配置和场景，不在运行中临时改口径。

### Goal 6：统计、审计和正式报告

完成 P5-P6；重建论文表格、图、统计摘要和最终文档，形成封版证据包。

### Goal 7：论文结果写入与最终复核

完成 P7；逐项核对论文数字与正式结果文件，完成最后一次一致性检查和提交。

## 六、明确的停止条件

遇到以下情况，应暂停正式运行并先修复，而不是继续堆数据：

- outcome、TSR、action assertion 和 final state 不一致。
- 正式结果混入 dev / test / check 目录。
- seed 数量不足或不同系统使用了不一致的 seed。
- 场景依赖 runner 中未在方案中声明的特判。
- Agent 结果实际来自 fallback，但报告将其标记为正式 Agent。
- 统计脚本读到了旧结果、覆盖结果或缺失结果。
- 为了得到更好数字而临时修改场景、指标或失败处理规则。

## 八、当前建议的下一步

下一次 Goal 优先执行“Goal 1：修复成功判定与指标一致性”。在这个问题没有解决前，不建议继续跑正式多 seed，也不建议继续扩展结果报告。因为如果任务成功定义本身有误，后续增加的样本只会稳定地产生错误统计。
