### 被测试的核心贡献

被测试的核心贡献包括：

> 1. **记忆过期机制**：半衰期衰减、硬过期 / 时间窗口过期、生命周期状态机（v4 §5）
> 2. **记忆更新操作**：完整的 add / merge / revise / invalidate / split / delete 集合，以及 provenance 与 coverage_proof（v4 §7）
> 3. **置信度校准**：非对称反馈、Memory Worth 分层、使用阈值（v4 §6）
> 4. **失活记忆治理**：双分支检测（重采样 vs 老化淘汰）+ 重采样（v4 §12.1）
> 5. **检索 / 规划门控**：候选隔离、注册表权威、歧义门（v4 §8、§11）

这分别是什么意思？

**1. 记忆过期机制**（那么记忆过期是什么时候更新这条记忆的状态的呢？是每次用到这条记忆的时候吗？还是每天定时呢？）
意思是：记忆不能永远默认正确。智能家居里的设备、偏好、位置、习惯都会变，所以系统要判断一条记忆什么时候还可信、什么时候该降权、什么时候不能再用于执行。

`半衰期衰减`：记忆越久没被验证，可信度越低。比如“用户睡觉喜欢空调 24 度”，半年没再出现过，就不能还像刚记住时一样确信。

`硬过期`：事实已经明确不成立，必须停止使用。比如 `switch.study_heater` 这个设备从 HA registry 里被移除了，所有关于“书房小太阳”的记忆都应该 expired，不能再调用它。

`时间窗口过期`：只在某段时间内有效。比如“这周每天晚上 7 点开客厅灯”，过了这周就不能继续执行。

`生命周期状态机`：每条记忆都有状态，比如 `candidate`、`active`、`stale`、`conflicted`、`superseded`、`expired`、`archived`、`deleted`。这比“有/没有记忆”更细，能表达“还可用”“过时了”“被新记忆替代了”“只保留审计但不执行”等不同情况。

**2. 记忆更新操作**（那么记忆更新时候的流程是什么呢？是一条新的记忆来了，然后就查询出相近的记忆吗？然后再决定操作？）
意思是：当系统发现新信息时，不能只做简单的 `update` 覆盖，而要区分“新增、合并、修订、失效、拆分、删除”等不同语义。

`add`：新增记忆。比如用户说“以后把书房台灯叫小书灯”，新增一条 alias。

`merge`：合并两条等价或互补记忆。比如两个会话都记了“小书灯=书房台灯”，可以合成一条，但必须确认没有丢信息。

`revise`：局部修订。比如原来“卧室灯=卧室顶灯”，后来用户说“以后卧室灯指床头灯”，新版本替代旧版本，旧的变 `superseded`。

`invalidate`：让某条记忆失效，但不一定删除。比如用户说“以后睡觉别自动调空调了”，原偏好不再用于规划，但仍可保留审计。

`split`：一条记忆太宽泛，要拆开。比如“客厅灯”可能指客厅顶灯、氛围灯、落地灯，长期导致歧义，就应该拆成更细的几条。

`delete`：用户明确要求忘掉，尤其是隐私内容。比如“把我常去健身房这件事忘掉”，应逻辑删除，并从 Chroma 向量索引移除，不能再被召回。

`provenance`：来源可追溯。系统要知道这条记忆来自用户明确陈述、用户纠错、HA registry、行为观察，还是 LLM 推断。

`coverage_proof`：合并证明。merge 时要证明合并后的记录完整覆盖原来两条记录的信息；如果没有这个证明，维护任务应该回滚合并，避免粗粒度记忆吞掉细节。

**3. 置信度校准**（置信度是什么条件/情况下更新呢）
意思是：系统不仅要知道“检索到了什么”，还要知道“这条记忆现在有多可信、历史上有没有用、能不能直接拿去执行”。

`非对称反馈`：一次失败比一次成功更重要。比如系统根据“小书灯=书房台灯”开错灯，用户纠正后，这条旧记忆的置信度应该明显下降；而一次成功只小幅增加置信度。师兄方案里 `α_neg=0.20`，`α_pos=0.04`，负反馈权重是正反馈的 5 倍。

`Memory Worth 分层`：衡量一条记忆“历史上是否真的有用”。高 MW 的记忆可以优先检索、延长半衰期；低 MW 的记忆降级为 dormant 或进入清理候选。

`使用阈值`：不同任务风险不同，所需置信度不同。查询任务阈值低，比如“卧室空调之前设多少度”可以带不确定性回答；普通控制任务阈值更高，比如“打开卧室加湿器”；安全动作最高，比如门锁、安防、自动化规则，低于阈值必须确认。

**4. 失活记忆治理**（失活记忆是什么意思？）
意思是：不是所有长期没用的记忆都应该立刻删。有些记忆没被用，不是因为内容没价值，而是描述太模糊，检索不到。

`双分支检测`：先判断一条死记忆为什么“死”。如果是描述模糊，比如自然语言写成“那个灯”，就走重采样；如果描述已经很清楚但长期不用，就走老化淘汰。

`重采样`：用结构化 payload 和关联记忆，把模糊描述重写得更具体。比如把“那个灯”重写为“书房台灯的小书灯别名”，给它一次重新被检索到的机会。

`老化淘汰`：如果内容清楚但长期无人使用，说明它可能价值低，就从 active 降为 stale / dormant / archived，必要时进入清理候选。

实验方案里 A4 测“模糊文本 → 重采样”，A6 测“非模糊老化 → archived”，就是为了验证这两条分支不是混在一起的。

**5. 检索 / 规划门控**
意思是：记忆被检索出来，不等于一定能参与执行。系统在规划动作前还要过滤、对齐权威来源、判断歧义和风险。

`候选隔离`：LLM 推断或单次行为观察只能是 `candidate`，不能直接控制设备。比如用户只手动设过一次空调 24 度，系统不能立刻记成“用户睡觉喜欢 24 度”并自动执行。

`注册表权威`：HA registry 对设备是否存在、实体绑定、服务能力具有最高权威。比如记忆里说“客厅顶灯支持色温”，但 HA registry 当前显示不支持，那必须以 registry 为准，不能调用不存在的能力。

`歧义门`：如果 top1 和 top2 候选差距不够大，系统不能硬猜，要追问。比如用户说“开卧室灯”，卧室有顶灯和床头灯，如果没有可靠别名，就应该问“你是指卧室顶灯还是床头灯？”

#### 追问答案

可以这样理解，我按你的四个追问分别回答，并尽量说清“什么时候触发”。

**1. 记忆过期机制：状态什么时候更新？**
不是只在“每次用到这条记忆时”才更新，也不是只靠“每天定时”一种方式，而是 **两类触发都有**。

第一类是 **读的时候现算**：
在实现方案里，`effective_confidence` 是“检索时动态计算”的，不是提前写死的 [师兄写的记忆实现方案.md (line 213)](/Users/shua/PycharmProjects/iot_agent/iot-agent-refactored/iot-agent-refactored_demo/师兄写的记忆实现方案.md:213)。
这意味着：

- 记忆虽然原始 `confidence` 没变
- 但一旦被拿来检索，就会根据“过了多久”“之前成功/失败多少次”重新算当前可信度
- 所以“软过期”很多时候是在**使用 / 检索时体现出来**

第二类是 **维护任务里批量迁移状态**：
方案里明确写了 maintenance 会做：

- 过期扫描
- 置信度衰减
- active 低于阈值进入 stale
- 冲突扫描
- 死记忆处理
  见 [师兄写的记忆实现方案.md (line 737)](/Users/shua/PycharmProjects/iot_agent/iot-agent-refactored/iot-agent-refactored_demo/师兄写的记忆实现方案.md:737)。

所以更准确地说：

- **硬过期 / 时间窗口过期**：通常由事件或 maintenance 扫描来更新状态
- **软过期**：检索时先体现在 `effective_confidence` 下降，maintenance 再把它正式迁到 `stale`
- **重新验证成功**：又可以从 `stale` 回到 `active`，见状态机 [师兄写的记忆实现方案.md (line 232)](/Users/shua/PycharmProjects/iot_agent/iot-agent-refactored/iot-agent-refactored_demo/师兄写的记忆实现方案.md:232)

一句话总结：
**过期不是单点触发，而是“检索时动态计算 + 定时维护正式迁移状态 + 外部事件立即失效”三者结合。**

**2. 记忆更新操作：流程是什么？**
你的理解基本对，流程就是“来了一条新信息，先找相近 / 相关旧记忆，再决定做哪种更新操作”。

实现方案给的流程是每轮对话结束后执行 [师兄写的记忆实现方案.md (line 349)](/Users/shua/PycharmProjects/iot_agent/iot-agent-refactored/iot-agent-refactored_demo/师兄写的记忆实现方案.md:349)：

1. `MemoryExtractor` 从当前对话抽取候选事实
2. `MemoryResolver` 判断它属于哪个 scope，比如 entity / room / user / routine
3. `MemoryMatcher` 查找已有相似记忆，或者同主语同谓词的记忆
4. `MemoryUpdatePolicy` 决定到底是 `add` / `merge` / `revise` / `invalidate` / `split` / `delete`
5. `MemoryWriteGate` 再检查来源、风险、置信度、隐私权限
6. 写入 canonical store
7. 同步更新 Chroma 索引

所以不是“新记忆一来就直接写”，而是：
**先抽取，再匹配旧记忆，再判断是新增、修订、合并还是让旧记忆失效。**

例如：

- 用户说“以后卧室灯指床头灯”
- 系统先匹配到旧记忆“卧室灯=卧室顶灯”
- 然后判断这不是普通 add，而是 `revise`
- 旧记录变 `superseded`
- 新记录变 `active`

**3. 置信度校准：什么情况下更新？**
置信度更新主要发生在 **执行结果出来之后**，以及 **用户明确纠错时**。

实现方案写得很直接 [师兄写的记忆实现方案.md (line 279)](/Users/shua/PycharmProjects/iot_agent/iot-agent-refactored/iot-agent-refactored_demo/师兄写的记忆实现方案.md:279)：

- **任务成功且该记忆被用到**
  - `positive_hits += 1`
  - `confidence` 小幅上升
- **任务失败且该记忆直接导致失败**
  - `negative_hits += 1`
  - `confidence` 明显下降
  - 状态可能变成 `stale` 或 `conflicted`
- **用户明确纠错**
  - 旧记忆直接 `superseded`
  - 新记忆高置信写入
- **只是长期没用**
  - 不改原始 `confidence`
  - 只通过 `effective_confidence` 自然衰减

所以要区分两个概念：

- `confidence`：原始置信度，主要在“成功、失败、纠错”时更新
- `effective_confidence`：当前有效置信度，检索时按时间衰减重新计算

这也是为什么文档说“长期没用不改原始 confidence，只让 effective_confidence 衰减”。

**4. 失活记忆治理：失活记忆是什么意思？**
“失活记忆”就是：**长期没有被成功访问、几乎不再参与检索、价值很低，处于沉睡状态的记忆。**

实现方案里对应的是 `dead memory`，判定条件大致是 [师兄写的记忆实现方案.md (line 746)](/Users/shua/PycharmProjects/iot_agent/iot-agent-refactored/iot-agent-refactored_demo/师兄写的记忆实现方案.md:746)：

- `access_count == 0` 且已经超过半衰期
- 或者长期从未被访问，时间已经非常久

它不一定是“错误记忆”，更常见的是两种情况：

- **内容其实有用，但描述太模糊**，导致检索不到
- **内容已经没什么价值了**，所以长期没人用

于是治理就分两条路：

- 如果是“描述模糊”，就 **重采样**：把自然语言描述重写得更具体
- 如果是“内容老了 / 价值低”，就 **降级、归档、清理**

所以“失活记忆”你可以把它理解成：
**不是已经错了，而是长期睡着了、不再活跃了，需要判断是救活还是淘汰。**

如果你愿意，我下一条可以继续把这四个问题画成一个很清晰的“小流程图版”：
“新记忆进来怎么处理”“旧记忆平时怎么衰减”“什么时候进入失活治理”。

### 核心研究问题

那么下面几个核心研究问题是如何验证的呢？：
> 核心研究问题
>
> **RQ1 — 记忆过期。** 与没有过期机制的系统相比，时间感知型管理（衰减 + 硬过期 + 时间窗口有效性）是否能减少过时记忆召回，并保持任务成功率？
>
> **RQ2 — 记忆更新。** 结构化的更新操作（merge / revise / invalidate / split / delete）是否比朴素覆盖写入更能维持记忆一致性与来源可追溯性？
>

>
> **RQ4 — 失活记忆治理。** 双分支的失活记忆检测 + 重采样，是否能在不丢失有价值信息的前提下提升存储效率与检索精度？

> **RQ5 — 端到端性能与成本。** 集成系统是否能在任务成功率以及用户满意度的操作化代理指标（澄清负担、不安全动作规避、偏好匹配）上优于各类基线，且 **上下文成本可接受**，也就是并非仅仅因为比大上下文基线消耗了更多 token 才取得优势？

`oracle planner 验证` 和 `agent planner 验证` 的区别是：

**1. Oracle planner 验证**
这是一个**规则固定、确定性的规划器**。
它不靠 LLM 临场自由发挥，而是按 заранее 写好的规则做决策。

作用是：
**尽量排除 LLM 推理波动，只测“记忆本身好不好”。**

比如：

- 如果记忆包里已经正确给出了候选设备
- oracle planner 就按固定规则选 top1，或者在歧义时发起澄清
- 它不会因为“这次模型抽风了”而选错

所以它主要用来验证：

- 记忆有没有召回对
- 过期机制对不对
- 更新后旧记忆有没有失效
- 候选隔离有没有起作用

文档里说，RQ1–RQ4 主要用 oracle planner，因为这些问题想测的是“记忆质量”，见 [实验方案-v3(1)-中文翻译.md (line 494)](/Users/shua/PycharmProjects/iot_agent/iot-agent-refactored/iot-agent-refactored_demo/实验方案-v3(1\)-中文翻译.md:494)。

**2. Agent planner 验证**
这是**真实的 LLM planner**。
它会像真正的智能体一样，拿着检索到的记忆去理解、推理、规划、决定动作。

作用是：
**看整套系统在真实使用方式下，最终表现怎么样。**

它测的是端到端效果，比如：

- 任务成不成功
- 会不会老追问用户
- 高风险动作会不会先确认
- token 成本高不高

所以它主要用来验证 `RQ5`，也就是“整套系统最终是不是更好”，见 [实验方案-v3(1)-中文翻译.md (line 496)](/Users/shua/PycharmProjects/iot_agent/iot-agent-refactored/iot-agent-refactored_demo/实验方案-v3(1\)-中文翻译.md:496)。

------

一句最简单的话：

- `oracle planner`：像“标准阅卷器”，主要测**记忆模块本身**
- `agent planner`：像“真实上场考试”，主要测**完整智能体最终效果**

关键区别是：**它们用的是同一套记忆系统，但“谁来根据这些记忆做最终决策”不一样。**

**先把两个东西分开**

- `记忆子系统`：负责存什么、怎么过期、怎么检索、怎么打分、怎么更新。
- `planner`：负责拿到这些记忆后，最后决定“是开哪盏灯，还是先追问”。

所以：

- `agent planner`：这个“最后拍板的人”是 LLM。
- `oracle planner`：这个“最后拍板的人”不是 LLM，而是一套固定规则。
  见 [实验方案-v3(1)-中文翻译.md (line 494)](/Users/shua/PycharmProjects/iot_agent/iot-agent-refactored/iot-agent-refactored_demo/实验方案-v3(1\)-中文翻译.md:494)

**oracle planner 不是“直接知道标准答案”**
它不是作弊，不是偷看 ground truth。
它只看**被测试系统吐出来的记忆检索结果包**，然后按固定规则做决策，见 [实验方案-v3(1)-中文翻译.md (line 499)](/Users/shua/PycharmProjects/iot_agent/iot-agent-refactored/iot-agent-refactored_demo/实验方案-v3(1\)-中文翻译.md:499)。

也就是说：

- 如果记忆系统已经把正确设备找出来了，oracle planner 就稳定地选它
- 如果记忆系统没找出来，oracle planner 也救不了
- 所以它测的仍然是记忆系统本身，只是把“LLM 临场发挥”这个噪声去掉了

**实际怎么跑**

可以把两者都理解成这条链路：

1. 用户一句话进来
2. 记忆系统去检索相关记忆
3. 形成一个“记忆包 / 候选包”
4. planner 根据这个包决定动作或澄清
5. 执行动作
6. 根据结果再回写记忆

差别只在第 4 步。

**Agent planner 怎么跑**

1. 用户说：“开卧室灯”
2. 记忆系统检索到：
   - alias：`卧室灯 -> 卧室床头灯`
   - 候选设备：卧室顶灯、卧室床头灯
   - 当前置信度：床头灯更高
3. 把这些内容组织成 prompt 发给 LLM
4. LLM 自己理解、推理，然后决定：
   - 直接开床头灯
   - 或者问“你是指顶灯还是床头灯？”
5. 执行，再根据成功 / 失败更新记忆

这里的问题是：即使记忆包一样，LLM 这次可能判断对，下次也可能判断歪一点。

**Oracle planner 怎么跑**

1. 用户说：“开卧室灯”
2. 记忆系统检索到的内容和上面**完全一样**
3. 不发给 LLM自由推理，而是交给固定规则：
   - 如果 top1 分数超过控制任务阈值
   - 且 top1 和 top2 差距大于歧义边界
   - 就选 top1
   - 否则就澄清
     这就是文档里说的 oracle planner 合约，见 [实验方案-v3(1)-中文翻译.md (line 499)](/Users/shua/PycharmProjects/iot_agent/iot-agent-refactored/iot-agent-refactored_demo/实验方案-v3(1\)-中文翻译.md:499)
4. 执行，再根据结果更新记忆

所以 oracle planner 的核心是：
**它不负责“想”，它只负责“按规则判”。**

**你问“oracle planner 不需要 LLM 来处理记忆吗”**
严格说，文档里的意思是：**在“规划决策”这一步，不用 LLM。**
它依赖的是记忆系统已经产出的结果包，而不是让 LLM 再自由解释一遍这些记忆。

所以最关键的区别不是“有没有记忆”，而是：

- `agent planner`：`记忆 -> LLM 决策 -> 动作`
- `oracle planner`：`记忆 -> 固定规则决策 -> 动作`

**为什么要搞 oracle planner**
因为他们想回答一个很关键的问题：

“最后表现差，到底是因为记忆没做好，还是因为 LLM 当场发挥不稳定？”

有了 oracle planner，就能更干净地测：

- 过期机制有没有让错记忆少被召回
- 更新机制有没有把旧记忆正确失效
- candidate 隔离有没有减少误执行
- 阈值门控有没有按规则生效

如果这些在 oracle planner 下都表现好，说明**记忆系统本身是对的**。
如果换成 agent planner 后效果掉了，问题更可能在 LLM 规划这层。

一句最直白的话：

- `oracle planner`：像裁判按规则判卷，不即兴发挥
- `agent planner`：像真实助手现场思考、现场决定

### 测试套件 —— 36 个确定性场景脚本

这里说的就是：**这份实验方案真正落地成了 36 条可执行的测试用例。**

前面的世界模型 `world_model/v1.json` 只是定义了“考场环境”；
而 **“36 个确定性场景脚本”** 定义的是：

- 用户会说什么
- 在什么时间说
- 中间世界会发生什么变化
- 系统正确时应该做什么动作
- 或者应该追问什么
- 或者记忆状态应该变成什么样

所以你可以把它理解成：

- `第 4 节`：准备一个固定的虚拟家
- `第 5 节`：在这个虚拟家里出 36 道固定考题

**“确定性”** 的意思是：
这些测试不是随机对话，不是临场发挥，而是**每一步都 заранее 写死**。

比如一个场景可能会写成这样：

1. `say`：t0 用户说“以后把书房台灯叫小书灯”
2. `expect_memory`：系统应该记住 alias(小书灯 → 书房台灯)
3. `say`：t0+1d 用户说“打开小书灯”
4. `expect_action`：系统应该执行 `light.turn_on(light.study_desk)`

这就叫一个“场景脚本”。

这些脚本里常见的步骤类型有：

- `say`：用户说一句话
- `event`：世界发生变化或故障注入
- `expect_action`：系统应该执行哪个动作
- `expect_clarify`：系统不该硬做，而应该追问
- `expect_memory`：系统的记忆状态应该变成什么样

所以第 5 节本质上是在回答：

**“你准备怎么具体测这些记忆机制？”**

不是只说“我要测记忆过期”，而是把它展开成具体 36 个场景，比如：

- 别名建立后能不能正确回忆
- 用户改口后旧记忆会不会失效
- 临时规则过期后还会不会误执行
- 设备从注册表移除后系统会不会继续调用
- 低置信度时会不会先追问
- 失败后会不会写 reflection 并避免再次踩坑

另外，这 36 个场景还按类别分组了：

- A：别名演化与治理
- B：偏好与习惯形成
- C：临时规则与时间窗口
- D：设备注册表变化
- E：例程与复合任务规划
- F：冲突、合并、拆分、删除
- G：负向对照与冷启动
- H：查询任务与阈值分层

一句话总结：

**第 5 节就是整套实验的“题库 + 标准答案 + 判分依据”。**
没有这一节，前面的研究问题就只是想法；有了这一节，实验才真正可执行。
