# SAE Memory System 实验结果分析

> 分析日期：2026-07-30
> 审阅对象：`实验进展-2026-7-26.md`、`iot-agent-refactored_demo/docs/实验方案-v3(1).md`，以及对应的场景、runner、memory、metrics、baseline、ablation、统计、审计与测试实现。

## 1. 总体结论

实验方案需要实质修改，并在修改实现后重跑关键实验。当前结果可以保留为“功能验证 / 探索性证据”，但还不适合作为论文最终主实验封版。

项目在工程上已经形成较完整的 benchmark：包括 36 个场景、Oracle/Agent 两种 planner、Ours 与 B0-B5、8 个消融、批量运行、统计、成本记录和严格审计。`7560/7560` unit 落盘以及无 fallback、无执行链 failure，说明实验执行完整性较好。

但是，严格审计 `pass` 只能证明任务执行和工件落盘符合 runner 预期，不能证明：

- 主指标符合实验方案定义；
- baseline 实现与名称一致且比较公平；
- ground truth 没有泄漏到被测系统；
- 统计推断覆盖了场景异质性；
- 实验测到的是完整产品 Agent，而不是简化实验组件。

因此，`实验进展-2026-7-26.md` 中“真实 Agent 结果可以作为论文正文主实验数据”的判断目前偏乐观。

## 2. 当前结果可以说明什么

现有结果能够较有力地说明：

1. 实验 harness 能稳定运行完整矩阵，并记录模型调用、断言、检索、执行和维护 trace。
2. 在场景直接给出正确 memory operation 的条件下，Ours 的实验版 MemoryService 能满足大部分预设机制契约。
3. 在当前固定场景、当前 planner prompt、当前 post-guard 和当前 composite success 定义下，Ours 的成功率高于现有 baseline 配置。
4. 当前实验实现具备进一步升级为论文级 benchmark 的基础。

现有结果尚不能充分说明：

1. Ours 在真实自然语言记忆写入、冲突发现和更新决策上优于 baseline。
2. Ours 的用户可见端到端任务成功率具有当前表格所示的优势幅度。
3. Ours 能独立识别并避免系统不知道的过期记忆。
4. Ours 的 Context Efficiency 优于真正的 full-history baseline。
5. ConflictHandling 是贡献最大的独立机制。
6. 当前结论能推广到长历史、跨 session、不同家庭、不同语言表达或不同模型。

## 3. P0：不修正就不应封版的问题

### 3.1 当前“TSR”与方案定义不一致

实验方案在 `docs/实验方案-v3(1).md:525` 和 `:567` 将 TSR 定义为最终设备状态是否与 ground truth 一致。

实际实现为：

- `experiments/runner/single_run.py:697-753`：memory assertion 失败会加入 `assertion_failures`；
- `experiments/runner/single_run.py:779-788`：action、clarification、memory、final-state 任一断言失败都会影响 `task_success`；
- `experiments/metrics/core.py:142-170`：该 composite `task_success` 被直接命名为 `TSR`；
- 真正接近方案定义的结果被单独命名为 `State TSR`。

这会系统性偏向 Ours。baseline 本来就不一定维护 Ours 定义的 candidate、superseded、conflicted、split-child 等内部状态，却仍然按照 Ours 的内部状态真值被处罚。

进展表本身已经暴露出明显差异：

| 系统 | 当前 TSR | State TSR |
| --- | ---: | ---: |
| Ours | 88.80% | 87.65% |
| B1 | 49.26% | 76.67% |
| B2 | 64.91% | 81.18% |
| B4 | 49.54% | 76.86% |
| B5 | 65.37% | 83.14% |

在当前代码上进行的一次诊断性强制 Oracle 复算（不是正式统计结果）也显示了这种偏差：

| 系统 | Composite success | 仅共同外部行为断言 |
| --- | ---: | ---: |
| Ours | 36/36 | 33/33 |
| B0 | 13/36 | 17/33 |
| B1 | 20/36 | 30/33 |
| B2 | 27/36 | 32/33 |
| B3 | 34/36 | 32/33 |
| B4 | 20/36 | 30/33 |
| B5 | 26/36 | 31/33 |

这不表示最终 Agent 外部 TSR 一定呈现同样数值，但足以证明当前 composite 指标包含显著的内部机制评分影响。

建议修改：

- 将当前 `TSR` 改名为 `Contract Conformance Score` 或 `Mechanism Conformance Score`。
- 论文主 TSR 只使用用户可观察的正确动作、正确不动作、最终状态和必要澄清。
- query、control、automation、safety 分开报告，不将异构任务强行压成一个未解释的分母。
- memory assertion 只进入 Oracle 机制验证，不进入 Agent 主 TSR。
- 每个指标明确 eligible scenario、分子、分母和缺失值处理方式。

### 3.2 场景把正确的 memory operation 注入了所有系统

Oracle 和 Agent 路径都会执行场景中的 `oracle_input.memory_ops`：

- `experiments/runner/single_run.py:418-422`
- `experiments/runner/single_run.py:892-895`

此外，`action_template` 可以把 planner 的抽象选择映射成场景隐藏真值中的 service、entity 和 args（`single_run.py:944-1005`）。

因此当前实验主要测量的是：

> 在已经知道正确记忆操作和部分正确动作结构后，系统能否完成存储、检索和执行。

它没有真正覆盖：

- 从自然语言抽取记忆；
- 判断是否应该写入；
- 自动发现冲突；
- 选择 revise、invalidate、merge 或 split；
- 错误记忆写入后的恢复；
- 多轮对话中的实体消歧和事实对齐。

更重要的是，实验运行的是 `experiments/memory/` 下的简化 MemoryService，而不是项目的 `try/memory/` 或 `smartHome/m_agent/memory/runtime_v1.py::DemoMemoryRuntime` 完整路径；Agent 也主要是 plan-only adapter，不等同于完整 smartHome Agent。

建议把实验明确拆为三层：

1. **Operation semantics benchmark**：允许 oracle memory op，只验证生命周期、治理和存储语义。
2. **End-to-end ingestion benchmark**：只提供原始用户话语，禁止 `memory_ops` 和 `action_template`。
3. **Integrated-system replay**：通过 adapter 运行实际 MemoryRuntime 与完整 Agent。

### 3.3 SRR 的 ground truth 不是独立真值

方案要求 `true_status` 由模拟时钟和标注独立计算，不能相信系统自身状态（`docs/实验方案-v3(1).md:568-569`）。

实际实现中：

- `experiments/memory/service.py:190-209` 先依据系统记录的 status 过滤 expired、superseded 等记录；
- `experiments/memory/service.py:239-249` 设置 `true_status=record.status`，直接复制系统自报状态。

这意味着：如果某个 baseline 不具备生命周期能力，它会继续把实际上已经过期的记忆报告为 active，而 evaluator 也会把它当成 active，SRR 仍为 0。这可以解释为什么进展表中所有系统的 SRR 都是 0。

建议修改：

- 建立 evaluator-owned lifecycle resolver；
- 使用独立的 semantic fact ID、valid-from/valid-until、revision lineage 和模拟事件计算真实状态；
- 系统输出的 status 只能作为 prediction，不能作为 ground truth；
- SRR 应对系统实际送入 planner 的 usable set 进行评分。

### 3.4 Context Efficiency 没有使用真实 API prompt tokens

当前 Agent runner 的 `estimated_prompt_tokens` 只估算 query 和检索记忆文本：

- `experiments/runner/single_run.py:903-905`
- `experiments/metrics/core.py:238-243`

它没有覆盖完整 system prompt、JSON schema、工具说明、candidate devices、世界状态和其他 planner payload。

已有 smoke trace 的抽样差异包括：

| 场景 | estimated tokens | API prompt tokens |
| --- | ---: | ---: |
| B6 | 11 | 993–1136 |
| E1 | 48 | 1962 |
| G1 | 3 | 946 |

按进展表中 Ours 的 `TSR=0.8880`、`Context Efficiency=45.82` 反推，公式使用的平均 prompt 只有约 19.4 个估算 token。与此同时，进展文档记录整个主实验使用了 65,431,252 prompt tokens，即每个 grid unit 平均约 8,655 个真实 prompt tokens。

因此，当前 Context Efficiency 数值以及“不是靠更多上下文获胜”的结论不能成立。

建议统一使用 `agent_usage_metadata.prompt_tokens`，并按系统、场景和任务类型分别汇总。若供应商缺少 usage，则使用与实际 tokenizer 和完整序列一致的离线计数，而不是仅计算 query 和记忆正文。

### 3.5 B4 不是方案规定的 full-history baseline

方案要求 B4 将完整原始交互历史塞入 planner prompt，并且无检索、无结构化记忆（`docs/实验方案-v3(1).md:477-485`）。

当前情况是：

- Oracle 路径在 `single_run.py:431-437` 有 raw-history 估算特判；
- Agent 路径在 `single_run.py:892-905` 没有相同的原始历史分支；
- B4 仍接收场景注入的结构化 MemoryRecord；
- `score_mode=large_context` 只改变 top-k/score 行为，不等于原始完整对话历史；
- B1 和 B4 反推的平均估算 token 几乎相同，也不符合历史持续增长的预期。

因此，B4 比较、Table 4、Figure 5 以及 context-collapse 论证需要重新实现和重跑。

真正的 B4 应满足：

- 输入为原始 conversation/event history；
- 不创建或读取结构化 MemoryRecord；
- 不使用 retrieval ranking；
- 明确上下文超限时的截断策略；
- 在持久化长历史 workload 上报告准确率、真实 token 和截断失败率。

### 3.6 其余 baseline 也存在名称与实现不一致

主要问题包括：

- `use_structure` 只出现在配置中，没有实质控制 MemoryService 的数据表示。
- B1 所谓 RAG-only 仍然使用结构化 MemoryRecord 和 gold memory operation，不是 raw utterance RAG。
- 检索主要是 deterministic lexical overlap，并不是方案描述的同一 embedding model。
- B5 是自定义 lexical、recency、importance、subject-match 的均值 heuristic，不能直接称为 Generative Agents 或 Mem0 published baseline。
- B3 的 `use_dynamic_confidence=False` 只改变检索时的取值，反馈路径仍可能更新 raw confidence。

建议：

- 为每个 baseline 写可执行的行为契约测试；
- 所有检索型系统统一 embedding、top-k、base model、tool schema 和可比较的 prompt；
- B5 改名为 `GA-inspired heuristic`，或者接入固定版本的公开实现；
- 所有超参数只在独立 validation set 上调整。

### 3.7 正式结果在当前仓库中无法复核

进展文档声明正式结果位于：

- `experiments/results/formal_v2/`
- `experiments/results/strict_main_agent_final_20260726_v4/`

但当前工作区的 `experiments/results/` 只有 tracked 的 `agent_llm_smoke`。同时项目根目录 `.gitignore:7` 忽略整个 `results/`。

因此当前环境无法检查正式 raw trace、strict audit、significance output 和最终表格之间是否一致。文档中的 audit pass 是结果声明，不是当前 checkout 可复核的证据。

建议发布一个不可变结果包，至少包含：

- manifest 与 code revision；
- 冻结的 matrix、scenario、world model 和 prompt；
- 每个文件的 SHA-256；
- 聚合表、统计输出和完整重建命令；
- 大体积 trace 的对象存储、DVC 或 Zenodo URI；
- 少量关键 trace 和全部最终聚合工件应进入版本控制。

## 4. P1：影响论文可信度的问题

### 4.1 消融实验没有可靠隔离目标机制

一次 deterministic Oracle 复算可以精确复现当前消融比例，并定位到固定失败场景：

| 消融 | 产生差异的主要场景 |
| --- | --- |
| −Decay | H2 |
| −Governance | A4、A6 |
| −CandidateGate | A3 |
| −ConflictHandling | A2、B4、B5、D1、D2、D3 |
| −Ripple | F3 |
| −Split | F5 |
| −AsymFeedback | 无差异 |
| −FeatureAbsorption | 无差异 |

主要归因问题：

- `−Decay` 实际关闭整个 dynamic confidence，不只是时间衰减。
- 方案的 control threshold 是 0.70，代码 `experiments/memory/confidence.py:29-34` 使用 0.56；H2 差异主要是阈值伪影。
- 多个冲突场景直接用场景 patch 写入 conflicted、invalidate 或 revise，未测试自动冲突检测。
- F1 直接提供 related IDs，没有真正尝试 merge，FeatureAbsorption 没有被触发。
- A5 手工 patch negative hits/status，AsymFeedback 很难产生独立效果。
- F5 由脚本直接提供 split 子记录，没有测试系统自动发现和生成 split。

因此目前不能把 `−ConflictHandling` 的 19.35 个百分点下降解释成“ConflictHandling 是最大贡献机制”。

每个消融场景应增加 mechanism activation check，例如：

- 冲突检测器是否实际被调用；
- merge/split 决策是否由系统产生；
- decay 前后有效置信度是否按预注册公式变化；
- ripple 是否由失败事件自动触发；
- 禁用单一机制时，其他配置是否保持完全一致。

### 4.2 Oracle 重复 seed 冗余，Agent 的统计单位不充分

Oracle 路径是确定性的，同一配置在 20/30 个 seed 下通常产生完全相同的结果。重复运行可以做工程稳定性检查，但不能形成新的统计信息。

Agent 当前以每个 seed 聚合固定 36 个场景，再将 30 个 seed 作为 sign test 的观测单位（`experiments/runner/batch_run.py:224-242`）。这主要反映 LLM sampling 变化，忽略场景异质性和“能否推广到其他任务”的不确定性。

所有 baseline 的 Holm 后 `p=9.31e-09` 很可能来自 30 个 seed 的差异全部同号，而不是不同比较恰好具有完全相同的证据强度。

建议统计方案：

- Oracle：每个 deterministic 场景运行一次，以 scenario 为 paired unit；使用 paired exact/permutation/bootstrap。
- Agent：保留 scenario × seed 二层数据，使用 two-way cluster bootstrap、GEE 或 mixed-effects logistic model。
- 二元指标报告 paired risk difference、95% CI、odds ratio 或 McNemar，而不是主要依赖 Cohen's d。
- 明确 Holm family 是“全部 system × primary metric”还是其他预注册范围。
- 进行 same-seed repeat、different-seed diversity 和 model fingerprint 检查，确认 seed 确实产生可测随机性。
- 样本量应来自功效或区间精度分析，而不是固定沿用 N=30/20。

### 4.3 其他指标实现与方案不完全一致

- **PM**：`experiments/metrics/core.py:147-159` 实际计算所有物理 action assertion 成功率，不是仅对 preference task 的偏好匹配率。
- **UAA**：`core.py:179-183` 对 safety task 只看 `safety_gated`，没有限定“置信度低于 0.85 的动作”；正确直接执行的高-MW动作可能被记为 0。
- **UC**：`core.py:43-53` 只检查“任意旧记录失效 + 任意新记忆可用”，没有绑定具体 old/new pair 和 post-correction step。
- **ECE**：使用 top memory confidence 对 composite task success，混入 planner parse、world execution 和内部 assertion failure，不能代表 memory calibration。
- **DMR**：使用 created_at 计算年龄，但 maintenance 使用 updated/observed/created 的最大值，口径不一致。

需要为每个指标增加手工构造的 positive/negative evaluator unit tests，确保方案公式和实现逐项对应。

### 4.4 当前数据并未支持全部研究结论

进展中的 Oracle 表显示：

- Ours ECE = 0.266；
- B3 ECE = 0.156；
- ECE 越低越好；
- Ours UC = 0.333；
- `−AsymFeedback` 没有变化。

因此目前不能声称动态 confidence calibration 或 asymmetric feedback 已经得到实验证实。更稳妥的表述是：当前功能场景支持部分生命周期和治理机制，但校准与反馈机制尚缺少有效覆盖。

### 4.5 并非 7560 个 unit 都发生了真实 LLM 调用

36 个场景共有 54 个 `say`，所以 API 调用数正好是：

`54 × 7 systems × 30 seeds = 11,340`

F1、F3、F4、F6 没有 `say`：

- `4 × 7 × 30 = 840` 个 unit 没有 LLM 调用；
- 约 6720 个 unit 至少包含一次真实 LLM 调用；
- 审计将其标记为 `no_agent_call_required`，并不等于真实 external-LLM unit。

建议把描述改为：

> 共完成 7560 个 Agent-grid units，其中 6720 个包含真实外部 LLM 调用，共产生 11,340 次 API 请求。

纯内部机制场景不应进入 Agent 端到端 TSR。

### 4.6 Agent 输出受到 hidden bridge、硬编码和 post-guard 影响

主要包括：

- E1 的 `routine.movie_mode` 三步执行由 runner 硬编码，LLM 只需选择 `routine.run`。
- `action_template` 可以把 `planner.select` 转换为隐藏真值动作。
- `agent_planner.py:408` 之后的 post-guard 会自动补 query answer、强制部分 safety gate 或覆盖 raw planner 判断。

这些机制可以作为产品安全层，但实验必须区分：

- raw planner accuracy；
- post-guard override rate；
- guarded-system end-to-end accuracy；
- 每类 guard 带来的收益和误伤。

### 4.7 场景缺少真正的长期性与外部有效性

当前 36 个场景主要是独立微场景：

- 每个 unit 重置世界和数据库；
- 每场景最多约 3 次 utterance；
- 只有一个家庭、约 12 个实体和少量 distractor；
- 不存在持续增长的历史、跨 session 污染和容量压力；
- 没有冻结的 unseen scenario set；
- 双标注文件尚未完成，κ 不能计算；
- 场景在 pilot/smoke 阶段被反复调整，存在对测试集开发的风险。

建议增加：

- 10–20 条跨 session longitudinal trajectory；
- history/memory size 梯度；
- 释义、口语、省略、错别字和噪声变体；
- 第二个 home/world；
- 独立 validation set 与一次性 held-out test set；
- 完成双标注并报告 agreement。

### 4.8 安全、HA Oracle 与隐私结论还需收紧

- HAOracle 对 capability、required args 和参数范围的校验不够严格，错误参数仍可能被世界模型接受。
- F7 主要实现 logical delete 和停止召回，原文仍可能保留在 memory_records 或 memory_events 中。
- 因此当前只能声称“删除后不再召回”，不能声称“隐私数据已经物理擦除”。

如果论文涉及安全或隐私 claim，应增加错误服务参数、危险组合动作、日志残留、备份残留和真正 erase semantics 的测试。

### 4.9 回归测试不是 hermetic

在 clean 环境执行 smoke suite 时，报告生成测试会依赖尚未生成且被 `.gitignore` 排除的 significance artifact，并可能直接改写 tracked 的 `docs/实验结果摘要.md`。

建议：

- 所有测试使用 `TemporaryDirectory`；
- 报告生成函数接受显式 input/output path；
- 测试自行生成全部依赖工件；
- 测试不能改写论文正式报告；
- CI 从 clean checkout 执行完整流程。

## 5. 建议的实验方案 v4

### 5.1 最小实验矩阵

| 实验层 | 输入与系统 | 重复方式 | 主要用途 |
| --- | --- | --- | --- |
| Functional Oracle | 31 个机制场景；Ours、必要 baseline 和 8 个消融 | deterministic 场景一次；另做参数/场景变体 | 验证生命周期、冲突、治理、merge/split、ripple 等机制 |
| Agent Behavioral | 所有含用户可观察结局的场景；Ours+B0-B5 | scenario × seed；N 由精度分析确定，初始可保留 30 | 外部 TSR、WDR、unsafe action、clarification、真实 token |
| End-to-end Ingestion | 原始自然语言；禁止 gold `memory_ops/action_template`；接实际 runtime | scenario × seed | 测抽取、写入、更新、冲突发现到执行的完整链路 |
| Longitudinal | 持久数据库、跨 session；history/memory size 梯度 | trajectory × seed | 测遗忘、污染、容量、B4 context collapse |
| Robustness | held-out 释义/噪声、第二个 home/world、第二模型代表性子集 | paired runs | 验证结论不是模板或单模型特例 |

### 5.2 建议的主指标

主指标应限定为用户可观察结果：

- Control Final-State TSR；
- Query Answer Accuracy；
- Automation Decision Accuracy；
- Wrong-Device Rate；
- Unsafe Action Rate；
- Necessary/Unnecessary Clarification Rate；
- 真实 prompt/completion tokens；
- end-to-end latency。

机制与诊断指标作为 secondary outcomes：

- 使用独立真值的 SRR；
- 绑定 old/new pair 的 UC；
- memory-use conditional ECE；
- mechanism activation 与 conformance；
- active/stale/deleted memory count；
- maintenance latency/tokens。

### 5.3 方案文档各章节的修改重点

- **§5 场景格式**：将 runtime input 与 hidden evaluator ground truth 完全分离。
- **§6 Baselines**：补充可执行行为规范和 fidelity test。
- **§7 Ablations**：加入 activation check，确保每次只关闭一个机制。
- **§8 Metrics**：冻结公式、eligible set、分母、聚合和缺失值策略。
- **§9 Planner Mode**：扩展为 Oracle semantics、Agent behavioral、Integrated end-to-end 三层。
- **§11 Trace**：同时记录 raw planner output、guard override、最终动作和真实 usage tokens。
- **§15 Validity**：增加 test-set development、ground-truth leakage、runtime divergence 和 artifact availability。
- **§16 Execution**：先跑小规模 pilot 与 evaluator audit，再冻结代码和 held-out set，最后运行正式矩阵。

## 6. 现有实验结果的处置建议

### 6.1 Oracle 结果

可以保留为 deterministic functional conformance benchmark，用于：

- 回归测试；
- 验证机制语义；
- 定位具体场景失败；
- 检查消融是否实际触发。

不建议继续增加 seed。修正 TSR 名称、SRR 真值和消融触发后，需要重算机制表。

### 6.2 30-seed Agent 结果

如果能找回完整正式 trace，可离线完成：

- 排除内部 memory assertion，重算外部行为指标；
- 使用 `agent_usage_metadata` 重算真实 token 和成本；
- 区分 raw planner 与 guarded result；
- 按 scenario × seed 重新做分层统计；
- 修正“真实 LLM unit”的数量表述。

这些重算结果仍应标记为 exploratory，因为 B4、baseline fidelity、gold memory operation 和完整 runtime 问题无法通过离线重算消除。

### 6.3 必须重跑的部分

- 真正的 B1 raw-text RAG；
- 真正的 B4 full-history；
- 修正后的独立 SRR；
- 禁止 gold memory operation 的 end-to-end ingestion；
- 接实际 MemoryRuntime 的 integrated replay；
- 重新设计并带 activation check 的关键消融；
- 长历史和 held-out workload。

## 7. 推荐执行顺序

1. 冻结 v4 的研究 claim、primary metrics 和 baseline 行为规范。
2. 修复 TSR、SRR、真实 token、baseline 和 hidden ground-truth bridge。
3. 为 evaluator、baseline fidelity 和 mechanism activation 增加单元测试。
4. 完成双标注、validation/held-out 切分和长期 workload。
5. 用 2–3 个 seed 跑 pilot，人工审计 trace 与指标分母。
6. 冻结 revision、场景、prompt、模型配置和统计方案。
7. 运行正式矩阵并发布可复核 artifact bundle。

在这些步骤完成前，不建议继续简单追加 seed。否则只会更精确地重复当前测量偏差。

## 8. 最终判断

当前项目不是“实验失败”，而是已经完成了一个工程质量较好的第一版 benchmark，但实验定义、ground truth 隔离、baseline fidelity 和统计推断还没有达到论文最终封版要求。

建议将当前结果定位为：

> 机制实现验证 + 固定 benchmark 下的探索性 Agent 结果。

完成 v4 修改并重跑关键矩阵后，才能将结果定位为：

> 可复现、可公平比较、能够支撑论文主要研究结论的正式实验。

## 9. 2026-08-14 实现复核与下一阶段

本文件第 3-7 节记录的是对旧 36 场景实验的诊断。当前 v4 已实质修复其中的 P0 工程问题：用户可观察 TSR 与内部机制指标已分离，evaluator truth 独立维护，B1/B4 契约已重建，真实 API usage 已进入指标，hidden bridge 已移除，正式统计按 scenario × replicate_id 配对并实现两层 clustered bootstrap、McNemar、sign-flip 与全 family Holm correction。HAOracle、guard override 归因、freeze/trace/strict audit 也已补齐。

人工标注完成后，下一阶段应按以下顺序执行：

1. 计算 annotation agreement，确认状态为 `complete`，并完成人工分歧裁决。
