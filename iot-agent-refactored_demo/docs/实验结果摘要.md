## 5. Full-Grid 成本外推

当前至少有两组可用外推样本，且差异很大，说明 full-grid 成本对场景抽样非常敏感：

| 预计 total tokens 区间 | `41746320 ~ 95248440` |

### 5.2 基于 v3 的估算

| 项目 | 估算值 |
| --- | --- |
| 完整主实验 unit 数 | `7560` |
| 预计 API 调用总数 | `13608` |
| 预计 input / prompt tokens | `16787736` |
| 预计 output / completion tokens | `804384` |
| 预计 total tokens | `17592120` |
| 预计 total tokens 区间 | `8898120 ~ 25983720` |
| 预计串行总延迟 | `47045819.71 ms` |

换算说明与当前判断：

- `33053455.20 ms` 约等于 `9.18` 小时串行 wall-clock 时间。
- `47045819.71 ms` 约等于 `13.07` 小时串行 wall-clock 时间。
- 当前仓库没有固化供应商单价，因此 `strict_main_agent.cost_estimate.json` 只输出调用量、token 和串行耗时，不硬编码费用金额。
- `v2` 与 `v3` 的外推从 `1759 万` 到 `6141 万` total tokens 不等，波动仍然很大。这意味着当前样本量仍不足以把 full-grid 成本估计视为稳定结论，下一轮仍应继续补更均衡的代表场景，而不是直接发起全量主实验。

## 7. 当前判断

- `formal_v2` 仍是当前唯一可直接进入论文主表的正式结果根。
- `real_llm_candidate_20260725_two_seed` 仍只是历史 candidate，不能覆盖 `formal_v2`。
- `strict_agent_pilot_20260726_v2` 已经证明：
  - 新 strict serial runner 能稳定拿到真实 `external_llm` 结果；
  - clean revision + no-fallback + trace/manifest/audit 链已经可用；
  - 在真实 LLM 下，`H2` 这类“query 合格、control 应澄清”的边界场景仍会出现真实行为失败。
- `strict_agent_pilot_20260726_v3` 已经证明：
  - 在更新后的 clean revision `fbedd87` 上，拒答、更新、routine、冲突四类路径都已再次拿到真实 `external_llm` 成功 trace；
  - `C1` 暴露了新的有效失败：模型会漏掉有效窗口内本应执行的 routine step，说明“到期/时间窗口”仍是 full-grid 前必须重点抽查的风险点。
- `strict_oracle_ablations_20260726_v1` 已经证明：
  - 8 个 Oracle 消融的新 strict 结果根可完整运行；
  - `5760` 个 unit 可以在单一 clean revision 下全部通过 strict audit。
- 当前离论文最终封版仍然至少差：
  - `strict_main_agent` 绝大多数 unit 尚未运行，即使合并 `v2 + v3` 也只覆盖 `15 / 7560`
  - 真实 LLM 下只有 `B6` 做了 `Ours + B0-B5` 的 paired pilot，且它仍停留在较早 clean revision 的 `v2`
  - 人工双标注、第三人裁决与 Cohen's κ 仍是 pending
